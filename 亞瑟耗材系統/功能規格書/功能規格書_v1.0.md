# 一、系統概述

本系統管理亞瑟環境清潔在多個服務場域的耗材需求預測、補貨、配送與庫存，並涵蓋設備維修支援。

| 項目 | 數量 |
|---|---|
| 服務場域 | 175 |
| API 端點 | 467（耗材相關 218） |
| 前端頁面 | 178（耗材相關 78） |
| 耗材資料表 | 47 |
| 耗材權限碼 | 21 |

## 核心設計原則

- **量定一次**：每月訂貨量在結單日鎖定，後續變更須經退回或緊急追加，避免反覆調整導致採購與配送失準。
- **事實單一來源**：到貨與否只認收貨端驗收，不採信單據狀態或供應商回報。
- **可解釋優先**：預測、配送排序、維修核價皆採規則與統計基準，每項判斷都能說出依據與比較基礎。
- **失敗要響**：預測引擎故障時不產生草稿（fail loud），不以預設值矇混過關。

# M1　AI 耗材需求預測

為每個「場域 × 品項」推估次月需求量，作為訂貨草稿的建議值。

## 演算法

```
建議量 ＝ baseline（近期水位穩健集成）
        × (1 ＋ 品項因子)
        × (1 ＋ 活動% × 品項敏感度)
```

- **baseline**：由 Python 引擎依近期用量計算，回看 3 年歷史（lookback_years: 3）
- **品項因子**：管理者逐站選擇參與哪些因子（假日天數等），採 opt-in
- **活動敏感度**：各品項獨立設定（衛生紙類設高、設備耗材設 0），敏感度為 0 時活動係數不生效

## 規律性判定

並非所有品項都適合自動產草稿。系統以「站 × 品項」為單位判定規律性：

1. 人工覆寫優先（RegularityOverride）——動態判定為主，人工只覆寫例外
2. 觀察窗達成熟門檻且有規律值 → 自動分類為常態／混合（進草稿）或間歇（不進草稿）
3. 觀察期未滿 → 退回品項主檔預設，並在畫面標示「還需幾個月」

冷啟動（無歷史）與間歇型品項的建議量為 0，需人工填量，畫面以來源標籤區分兩者成因。

## 資料流

1. **取歷史**：系統彙整各場域歷史用量與共變數（來源 CS_StockMove／CS_OrderItem）
2. **呼叫引擎**：POST 至 :8100/forecast/generate-base 取得 baseline（外部 Python 服務）
3. **套用因子**：依站別因子旗標與品項敏感度計算最終建議量
4. **寫入快照**：定版存入 CS_Forecast，供看板、草稿、回填三處共用（僅 15 號排程與回填加品項可寫入）

> **兩個入口，狀態不同。**
> /api/ai/forecast/* 為手動呼叫入口，受 AI_FORECAST_ENABLED 控制，目前**未啟用**（回 503）。
> 而月節奏實際使用的是耗材模組內的 forecastBySite，**不受該旗標限制、目前正常運作中**——最近一次產草稿為 2026-08-21，已涵蓋本月與次月。兩者呼叫同一個引擎，但用途與開關狀態不同。

## 校準

每月 5 號 02:00 自動以上月實際叫貨量回填預測，計算 WAPE 準確率，供後續調整參考。

# M2　AI 補貨建議

將預測結果轉為現場可操作的訂貨草稿，並提供供應商備料前視資訊。

## 對內：月訂貨草稿

1. **系統產草稿**：每月 15 號依預測產出次月訂貨單，狀態「草稿」（排程自動）
2. **場域回填**：現場主管檢視建議量並調整為實際需求（場域主管　CSF-FILL）
3. **結單鎖定**：25 號結單，未回填者自動採納系統建議值送覆核（排程自動）
4. **總部覆核**：審查異常量後推進發單（審查人／總部　CSA-REVIEW）

回填時若現場已調整過數量，系統重算預測不會覆蓋現場填的值——僅更新建議量欄位，實填量保留。判定方式為「填的量是否等於原建議量」。

## 對外：供應商備貨資訊

| 功能 | 內容 | 資料條件 |
|---|---|---|
| 補貨建議 | 次月各品項預估需求 | 該品項有預測量 **且** 該供應商供貨 |
| 備貨預測 | 供應商所有可供品項的未來兩個月預估 | 以「品項×供應商」關聯為基底 |

> 兩者資訊重疊：備貨預測已包含每個品項的次月預測量，補貨建議僅是其中「有需求」的子集。可能出現「備貨預測 42 筆、補貨建議 0 筆」的情形，需在畫面上說明差異，或整併為單一頁面。**此項已提列待決。**

# M3　異常預警

六類型自動巡檢，依嚴重度分級並可指名供應商協同處理。

| 代碼 | 類型 | 偵測邏輯 | 巡檢頻率 | 通知供應商 |
|---|---|---|---|---|
| LOW_STOCK | 低庫存 | 帳面量低於安全量之比例 | 每日 08:00 | 僅 HIGH 外發 |
| OVERUSE | 異常消耗 | 用量超出基準，按週切分事件 | 每日 08:00 | — |
| RPT_DELAY | 回報遲延 | 結單前一天 MID、當天 HIGH | 每日 08:10 | — |
| SUP_DELAY | 供貨延遲 | 逾期 1 天 LOW、3 天 MID、7 天 HIGH | 每日 08:10 | 是 |
| NO_REORDER | 長時間未補貨 | 距上次入庫天數 | 每週一 08:20 | — |
| SURGE | 需求異常增加 | 月中滾動偵測，及時調整當月叫貨 | 每週一 08:30 | — |

## 分級與去重

- 三級制 LOW／MID／HIGH，門檻參數可由各企業覆寫，設定異常時自動退回預設值而非拋錯
- 以 DedupeKey 去重：同一站同一品項的低庫存視為同一事件，不重複開單
- 複合升級：回報遲延若同時存在未結案的低庫存，直接升為 HIGH——延遲加缺貨才是真正會斷料
- 小站（領用型場域）不納入低庫存偵測與安全水位計算，避免每日誤報

## 供應商協同回覆

1. **系統開單**：偵測到異常並指名該品項的供應商（排程自動）
2. **供應商回覆**：三選一——已收到／改期到貨（填新日期）／供貨有困難（供應商平台）
3. **留痕與通知**：回覆存入紀錄，並推播站內通知給內部人員

> **回流路徑未完成。** 通知對象目前為「該場域主管，若無則預設帳號」，而 175 個場域僅 11 個設有主管；且異常中心畫面尚未顯示供應商回覆內容。供應商回覆後，總部實際上不易看見。**此為已知缺口，建議優先補足。**

# M4　供應鏈協同配送管理

將分散的配送需求整併為批次，排定順序並追蹤出車到貨。

## 整併規則

系統不做路徑最佳化（無場域座標資料，且計畫書未承諾 VRP／TSP），改採**可解釋的規則排序**：

- **急件優先**：依急迫分數排序——逾期 +40、剩 2 日內 +25、剩 5 日內 +10；併有未結案低庫存 +30；來自異常複核 +20（上限 100）
- **同行政區相鄰**：由地址解析縣市與區鄉鎮，同區集中
- **主站帶分站**：同一主站底下的分站併同一車
- **整併時間窗**：3 日內的需求可併為同批

## 批次狀態機

1. **採納建議，建立批次** → 狀態「草稿」，此時仍可調整站點（總部　CSF-DISPATCH）
2. **確認排單** → 狀態「已排定」，內容鎖定
3. **出車** → 狀態「配送中」，同時為批內各配送單寫入出貨日
4. **完成** → **系統自動推導**：批內所有配送單皆完成驗收即為完成，無須人工點選

> **「出車」是配送狀態能前進的唯一路徑。** 供應商端看到的「配送中」取決於配送單上的出貨日，而該欄位僅在出車時寫入。未編入批次的配送單將停留在「待出貨」，直到驗收後直接跳為「已到貨」。若實務上並非每批貨都經排單，需考慮開放單張配送單出車。

## 供應商可見範圍

供應商平台為**純資訊呈現**，除異常通知回覆外不提供任何流程操作。此為既定設計：供應商多有自有進銷存系統，要求其重複登錄不切實際，故系統只認內部人員確認的事實。

| 分頁 | 內容 | 資料來源 |
|---|---|---|
| 我的訂單 | 指派給該供應商的採購單 | CS_PurchaseOrder |
| 配送資訊 | 自該供應商出貨的配送單與狀態 | CS_Transfer（FromType=SUPPLIER） |
| 異常通知 | 指名該供應商的預警，可回覆 | CS_Alert |
| 補貨建議／備貨預測 | 次月與未來兩月需求前視 | CS_Forecast × CS_ItemSupplier |
| 我的維修單 | 派工給該供應商的維修案件 | MT_RepairOrder |
| 我的數據 | 採購單數、金額、品項統計 | CS_PurchaseOrder |

# M6　維修支援

設備資產管理、報修流程、時效追蹤與汰換決策。

## 報修狀態機

```
待受理 → 已派工 → 處理中 → 已完工
   └────────┴────────→ 已作廢（誤報）
            └────────→ 待受理（退回補件）
```

狀態轉換規則寫為純函式，由前端按鈕、後端驗證與決策代理三處共用，避免規則分歧。

## SLA 時效

四階段時效標準**由使用者自行設定**，程式內預設值僅為起點。設定損壞時自動退回預設而非中止排程。

> 內建預設值係依一般維修實務給定，**非亞瑟現行服務水準約定**。畫面應標示「暫定」，待累積三個月實際資料後以中位數回頭訂定。

## 決策支援

提供核價、調度比對與三案年化成本試算，全部採規則與統計基準，不使用語言模型。理由是這類判斷必須說得出依據——「報價偏高」若無法指出比較基準與差額，維修業者不會接受，總部也無從議價。

# 四、月節奏與排程

耗材訂貨以月為週期運作，關鍵時點如下。

| 時點 | 動作 | 說明 |
|---|---|---|
| 15 號 | 系統產次月訂貨草稿 | 依預測引擎基準值；引擎故障則中止不產 |
| 18 號起 | 回填催辦 | 提醒未回填場域，結單前一日再送最後通知（站內通知） |
| 25 號 | 結單鎖定 | 量定一次；未回填者自動採納系統建議值送覆核 |
| 26 – 次月 10 號 | 配送執行 | 配送量可分批或短收，入庫只入允收量 |
| 次月 5 號 | 預測校準 | 以上月實際叫貨回填，計算 WAPE |

## 每日／每週巡檢

- 08:00 庫存面（低庫存、異常消耗）
- 08:10 流程面（回報遲延、供貨延遲）
- 週一 08:20 長時間未補貨；週一 08:30 需求異常增加
- 09:30 回填催辦；每月 1 號 03:00 安全水位重算

# 五、權限模型

以功能碼搭配資料範圍雙層控管。

## 權限碼分群

| 前綴 | 領域 | 代表功能 |
|---|---|---|
| CSM- | 主檔設定 | 合約、場域、商品、供應商、採購限制 |
| CSF- | 訂貨流程 | 回填、採購單、閘門、配送排單、收貨 |

| CSG- | 管理面板 | 預算、營運指標 |

## 資料範圍

- **總部**：可見全部場域；為代填兜底角色
- **場域主管**：僅限自轄場域
- **供應商**：僅限與自身相關的訂單、配送、預警

> 內部人員與供應商的登入狀態**分開儲存**，可同時保持兩邊登入而不互相覆蓋。此為 2026-08-25 修正項——先前共用同一份儲存，導致測試供應商平台後無法進入內部系統。

# 六、部署與運維

| 服務 | 部署方式 | 備註 |
|---|---|---|
| API | PM2（dispatch-api） | 部署腳本驗證完整 dist 樹雜湊並保存 rollback |
| 前端 | 靜態站 | 獨立網域，與 API 分離 |
| 預測引擎 | 獨立 Python 服務 | 內網 :8100 |
| Redis | 容器 | BullMQ 佇列 |

> **兩項運維風險。**
> **其一**，預測引擎位址寫在程式碼的 fallback 預設值中，且無 kill-switch；引擎中斷將直接導致 15 號排程失敗。建議納入可用性監控。
> **其二**，執行中的引擎目錄與程式庫內的版本為兩份不同 checkout，存在版本漂移風險，需訂定明確的部署流程。

## AI 功能旗標

系統另有七項 AI 輔助功能（報表檢索、報表問答、智慧派工建議、請假瓶頸偵測、合約續約風險、問卷情緒分析、預測手動入口），**全部預設關閉**，啟用需設定對應環境變數並重啟；前端介面另需以 build-time 旗標重新建置。此設計使各功能可獨立評估後逐一開放。
